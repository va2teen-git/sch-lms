# Правила работы для ИИ-агентов (AI Workflow)

Так как разработка проекта School LMS полностью ведется автономными ИИ-агентами, к процессу взаимодействия с кодом применяются строгие правила во избежание деградации кодовой базы, потери контекста или нарушения работы боевого сервера.

---

## 1. Изоляция Продакшна и Запрет Работы в `D:\school-lms`

Боевой сервер запущен непосредственно из директории `D:\school-lms` и обслуживает реальных школьников на порту `8080`. Процесс Node.js удерживает открытые дескрипторы файлов в `dist/`, а в локальную базу `telemetry.db` непрерывно поступают данные.

### 🚫 Категорически запрещено внутри каталога `D:\school-lms`:
1. Переключать ветки Git (`git checkout <branch>`).
2. Запускать сборку (`npm run build`), так как на Windows файлы в `dist/` заблокированы процессом Node, что вызовет ошибку `EBUSY / EPERM` или поломку бандла.
3. Запускать dev-сервер (`npm run dev`) или автотесты (`npm test`, Playwright). Автотесты отправляют тестовые события телеметрии и сбросы, которые загрязнят боевую базу данных учащихся.

## 2. Стандартный Рабочий Процесс: Изолированный `git worktree`

Любая задача (разработка урока, фикс багов, изменение UI, обновление документации) выполняется **ИСКЛЮЧИТЕЛЬНО** в изолированном рабочем дереве `git worktree` по пути `D:\school-lms-dev`.

### Шаг 1: Создание рабочего окружения
Находясь в `D:\school-lms`, агент создает рабочее дерево под новую ветку:

```powershell
# 1. Создать worktree с новой веткой (например, content/lesson-10-level1)
git worktree add -b type/task-name D:\school-lms-dev

# 2. Мгновенно связать зависимости без дублирования дискового пространства
cmd /c mklink /J "D:\school-lms-dev\node_modules" "D:\school-lms\node_modules"
```

### Шаг 2: Разработка и отладка в `D:\school-lms-dev`
Все дальнейшие действия агент выполняет в каталоге `D:\school-lms-dev`:
* Запуск сервера разработки при необходимости: `npm run dev` (запускается на порту `4321` и не мешает продакшну на порту `8080`).
* Все события телеметрии и локальные тесты работают с собственной изолированной базой данных `D:\school-lms-dev\telemetry.db`.
* Прогон автотестов: `npm run test:contracts` и `npm test`.

## 3. Оформление Коммитов и Pull Request

Коммиты должны быть атомарными и следовать формату Conventional Commits:
* `feat:` — новый функционал.
* `fix:` — исправление ошибки.
* `docs:` — изменения в документации.
* `content:` — добавление или изменение уроков/заданий.

Пример:
```bash
git commit -m "content: добавлены задания для урока 10 класса по сетям"
git push -u origin type/task-name
```

Создайте Pull Request через GitHub CLI:
```bash
gh pr create --title "..." --body "..."
```

---

## 4. Обязательная Очистка Dev-Окружения (Worktree Cleanup)

После отправки ветки в репозиторий и создания PR (или после слияния) агент **ОБЯЗАН** удалить временное рабочее дерево, чтобы не оставлять заблокированные папки и не мешать следующим задачам:

```powershell
# Из основного каталога D:\school-lms:
# ВАЖНО: На Windows перед удалением worktree обязательно отвязать junction на node_modules:
if (Test-Path "D:\school-lms-dev\node_modules") { cmd /c rmdir "D:\school-lms-dev\node_modules" }
git worktree remove D:\school-lms-dev --force
```

Если по какой-то причине директория осталась заблокированной, проверьте отсутствие запущенных процессов dev-сервера в `D:\school-lms-dev` и повторите удаление.

## 5. Регламент Обновления Боевого Сервера в `D:\school-lms`

После того как Pull Request проверен и смержен в ветку `main`, для применения изменений на работающем боевом сервере в основной директории `D:\school-lms` выполняется строго регламентированная процедура:

```powershell
# 1. Получить свежие изменения из ветки main
git checkout main
git pull origin main

# 2. Обновить зависимости (если менялся package.json)
npm install

# 3. Выполнить миграцию базы данных (если менялась схема телеметрии)
node scripts/migrate_telemetry.js

# 4. Собрать продакшн-бандл
npm run build

# 5. Мягко перезапустить сервис
# Завершаем текущий процесс Node; сторожевой скрипт start_server.ps1
# автоматически перезапустит сервер с новым кодом в течение 2 секунд:
Get-Process -Name node | Where-Object { $_.Path -like '*node.exe*' } | Stop-Process
```

> **Важно:** Благодаря циклу `while($true) { node ./dist/server/entry.mjs; ... }` в `start_server.ps1`, при завершении процесса Node перезапуск происходит мгновенно, без разрыва цикла мониторинга.

## 6. Использование Контекста и Документации
* Агенту **ЗАПРЕЩАЕТСЯ** "гадать" или писать код по памяти.
* Перед началом работы агент **ОБЯЗАН** прочитать `AGENTS.md` и загрузить в контекст только те `.md` файлы из папки `docs/`, которые непосредственно относятся к задаче.
* Агент должен использовать утилиты для просмотра структуры файлов (например, `Get-ChildItem` в PowerShell), чтобы убедиться в существовании файлов, прежде чем пытаться их изменить.

---

## 7. Изоляция Изменений (Zero-Breakage Policy)
* Изменяя существующий компонент или логику (например, `Layout.astro` или `[id].astro`), агент должен минимизировать область изменений.
* Запрещается удалять существующие `id`, классы или функции, если это явно не требуется задачей, так как от них могут зависеть другие скрипты или тренажеры (iframe).

---

## 8. Защита Данных
* ИИ-агенту строго запрещается снимать комментарии с исключений в `.gitignore`. База данных `telemetry.db` и файлы с секретами (например, `.env`) **никогда** не должны попадать в индекс git.

---

## 9. Планирование и Пошаговая Реализация (Micro-planning)
* Получив объемную задачу (например, "Разработать урок"), агент **ОБЯЗАН** разбить ее на микро-шаги.
* Не пытайтесь реализовать теорию и все три уровня тренажеров за один шаг. Составьте план и двигайтесь строго пошагово.
* Каждое логическое действие должно быть проверено перед переходом к следующему.

---

## 10. Остановка при Трудностях (Fail-Safe)
* Если агент сталкивается с непредвиденными трудностями, ошибками фреймворка, падением сборок или если задача не укладывается в архитектуру — **АГЕНТ ОБЯЗАН НЕМЕДЛЕННО ОСТАНОВИТЬСЯ**.
* Категорически запрещено пытаться "угадать" решение путем бесконечных итераций переписывания кода (галлюцинаций). Сделайте паузу, детально опишите проблему пользователю ПК и ждите его решения/разрешения.

---

## 11. Работа с GitHub CLI (`gh`)
* На рабочем ПК установлена и авторизована утилита GitHub CLI (`gh`).
* Агент должен использовать ее для интеграции с репозиторием (например, для создания Pull Request: `gh pr create` или закрытия задач: `gh issue close`).
* Если для задачи существует Issue, агент должен связать свои изменения с этим номером.
