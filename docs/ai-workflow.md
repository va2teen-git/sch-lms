# Правила работы для ИИ-агентов (AI Workflow)

Так как разработка проекта School LMS полностью ведется автономными ИИ-агентами, к процессу взаимодействия с кодом применяются строгие правила во избежание деградации кодовой базы, потери контекста или нарушения работы боевого сервера.

---

## 1. Изоляция Продакшна и Запрет Работы в `D:\school-lms`

Боевой сервер запущен непосредственно из директории `D:\school-lms` и обслуживает реальных школьников на порту `8080`. Процесс Node.js удерживает открытые дескрипторы файлов в `dist/`, а в локальную базу `telemetry.db` непрерывно поступают данные.

### 🚫 Категорически запрещено внутри каталога `D:\school-lms`:
1. Переключать ветки Git (`git checkout <branch>`).
2. Запускать сборку (`npm run build`), так как на Windows файлы в `dist/` заблокированы процессом Node, что вызовет ошибку `EBUSY / EPERM` или поломку бандла.
3. Запускать dev-сервер (`npm run dev`) или автотесты (`npm test`, Playwright). Автотесты отправляют тестовые события телеметрии и сбросы, которые загрязнят боевую базу данных учащихся.

## 2. Стандартный Рабочий Процесс: Изолированный `git worktree`

Любая задача (разработка урока, фикс багов, изменение UI, обновление документации) выполняется **ИСКЛЮЧИТЕЛЬНО** в изолированном рабочем дереве `git worktree` по пути `D:\school-lms-dev`.

### Шаг 1: Создание рабочего окружения
Находясь в `D:\school-lms`, агент создает рабочее дерево под новую ветку:

```powershell
# 1. Создать worktree с новой веткой (например, content/lesson-10-level1)
git worktree add -b type/task-name D:\school-lms-dev

# 2. Мгновенно связать зависимости без дублирования дискового пространства
cmd /c mklink /J "D:\school-lms-dev\node_modules" "D:\school-lms\node_modules"
```

### Шаг 2: Разработка и отладка в `D:\school-lms-dev`
Все дальнейшие действия агент выполняет в каталоге `D:\school-lms-dev`:
* Запуск сервера разработки при необходимости: `npm run dev` (запускается на порту `4321` и не мешает продакшну на порту `8080`).
* Все события телеметрии и локальные тесты работают с собственной изолированной базой данных `D:\school-lms-dev\telemetry.db`.
* Прогон автотестов: `npm run test:contracts`, `npm run test:personas` и `npm test`.

### 2.1 Параллельная работа нескольких ИИ-агентов (Multi-Agent Parallel Workflow)

Если над проектом одновременно работают два или более независимых ИИ-агента (например, один создаёт новый урок, а второй внедряет серверный функционал или исправляет баги), **КАТЕГОРИЧЕСКИ ЗАПРЕЩАЕТСЯ** использовать одну и ту же рабочую директорию `D:\school-lms-dev`.

> ⚠️ **ПОЧЕМУ НЕЛЬЗЯ РАБОТАТЬ В ОДНОЙ ПАПКЕ DEV:**
> 1. В одной директории Git может быть активна **только одна ветка**. Переключение ветки одним агентом разрушит рабочую область второго агента.
> 2. Параллельные вызовы `git add / commit` приведут к фатальным блокировкам `index.lock: File exists`.
> 3. Изменения файлов начнут перезаписывать друг друга, приводя к невалидному коду и падению сборки.
> 4. Dev-серверы столкнутся по порту `4321` (`EADDRINUSE`).

#### Правило именования параллельных Worktrees:
Каждому агенту выделяется собственная изолированная папка:
* **Агент 1:** `D:\school-lms-dev` (порт dev-сервера `4321`);
* **Агент 2:** `D:\school-lms-dev-2` (порт dev-сервера `4322`);
* **Агент 3:** `D:\school-lms-dev-3` (порт dev-сервера `4323`).

#### Пошаговые команды для параллельного агента:
```powershell
# 1. Из основного каталога D:\school-lms создать выделенный worktree от свежего origin/main:
git fetch origin main
git worktree add -b type/task-name D:\school-lms-dev-2 origin/main

# 2. Мгновенно связать зависимости без дублирования дискового пространства:
cmd /c mklink /J "D:\school-lms-dev-2\node_modules" "D:\school-lms\node_modules"

# 3. Вся работа, тесты и сборка ведутся ИСКЛЮЧИТЕЛЬНО в D:\school-lms-dev-2:
# Запуск dev-сервера (при необходимости) только на свободном порту:
npx astro dev --port 4322

# 4. Проверка сборки и автотестов внутри своего окружения:
npm run build
npm run test:contracts

# 5. Отправка ветки и создание PR:
git push -u origin type/task-name
gh pr create --title "..." --body "..."

# 6. Обязательная очистка своего worktree после слияния:
cmd /c rmdir "D:\school-lms-dev-2\node_modules"
git worktree remove D:\school-lms-dev-2 --force
```

#### Регламент синхронизации при параллельном слиянии (Rebase Hygiene):
Если второй агент успел влить свой PR в `main` раньше вас:
1. В своём worktree выполните подтягивание актуального `main`:
   ```powershell
   git fetch origin main
   git rebase origin/main
   ```
2. Убедитесь, что `npm run build` и автотесты проходят без ошибок.
3. Обновите свой PR принудительным пушем безопасной версией:
   ```powershell
   git push origin <ваша-ветка> --force-with-lease
   ```

## 3. Оформление Веток, Коммитов и Pull Request

В проекте строго соблюдается модель **GitHub Flow** (короткоживущие ветки):

### 3.1 Конвенция именования веток:
Каждая задача создается строго в отдельной ветке от актуального `main` с понятным префиксом:
* `content/<grade>-class-lesson-<id>-<topic>` — разработка или правка уроков (например, `content/8-class-lesson-8-logic-operations`).
* `feat/<name>` — новый компонент UI, новый эмулятор или механика.
* `fix/<name>` — исправление бага в коде или стилях.
* `test/<name>` — добавление или доработка автотестов (включая сценарии персон `*-student-personas.spec.js`).
* `docs/<name>` — обновление документации и регламентов.

### 3.2 Формат коммитов (Conventional Commits):
Коммиты должны быть атомарными:
* `content:` — добавлены задания/теория для урока.
* `feat:` — новый функционал или механика.
* `fix:` — исправление ошибки.
* `test:` — добавление тестов Playwright.
* `docs:` — изменения в документации.

### 3.3 Жизненный цикл ветки и Pull Request:
1. Создание ветки: `git checkout -b <тип>/<название>`
2. Атомарный коммит: `git commit -m "content: добавлены задания для урока 8 класса"`
3. Отправка ветки: `git push -u origin <тип>/<название>`
4. Создание PR через GitHub CLI:
   ```bash
   gh pr create --title "..." --body "..."
   ```
5. **Обязательное удаление ветки при слиянии (Branch Hygiene):**
   * Ветки в Git живут только до момента слияния PR. Хранить старые замерженные ветки **категорически запрещено**.
   * При слиянии через CLI всегда используйте флаг `--delete-branch`:
     ```bash
     gh pr merge <PR_NUMBER> --merge --delete-branch
     ```
   * При локальной очистке удаляйте локальную ветку: `git branch -d <branch>`
   * Для удаления следов удалённых на GitHub веток используйте:
     ```bash
     git remote prune origin
     ```

## 4. Обязательная Очистка Dev-Окружения и Фоновых Процессов (Cleanup)

### 4.1 Удаление временного Worktree:
После отправки ветки в репозиторий и создания PR (или после слияния) агент **ОБЯЗАН** удалить временное рабочее дерево, чтобы не оставлять заблокированные папки и не мешать следующим задачам:

```powershell
# Из основного каталога D:\school-lms:
# ВАЖНО: На Windows перед удалением worktree обязательно отвязать junction на node_modules:
if (Test-Path "D:\school-lms-dev\node_modules") { cmd /c rmdir "D:\school-lms-dev\node_modules" }
git worktree remove D:\school-lms-dev --force
```

### 4.2 Очистка фоновых процессов в Shell (No Orphan Daemons Policy):
* Агенту **категорически запрещено оставлять висящие фоновые процессы** в shell (тестовые node-сервера, dev-серверы, скрипты автоперезапуска `while($true)`, фоновые запросы `curl`).
* Висящие процессы блокируют порты, нагружают процессор и удерживают блокировки файлов.
* **Перед завершением каждого хода** агент обязан проверить список запущенных фоновых задач (`manage_task list`) и остановить все процессы (`manage_task kill`), которые больше не требуются.
* Боевой сервер обслуживается независимой системной службой на порту `8080`, агент не должен оставлять собственные демоны в сессии диалога.

## 5. Регламент Обновления Боевого Сервера в `D:\school-lms`

После того как Pull Request проверен и смержен в ветку `main`, для применения изменений на работающем боевом сервере в основной директории `D:\school-lms` выполняется строго регламентированная процедура:

```powershell
# 1. Получить свежие изменения из ветки main
git checkout main
git pull origin main

# 2. Обновить зависимости (если менялся package.json)
npm install

# 3. Выполнить миграцию базы данных (если менялась схема телеметрии)
node scripts/migrate_telemetry.js

# 4. Собрать продакшн-бандл
npm run build

# 5. Мягко перезапустить сервис
# Завершаем текущий процесс Node; сторожевой скрипт start_server.ps1
# автоматически перезапустит сервер с новым кодом в течение 2 секунд:
Get-Process -Name node | Where-Object { $_.Path -like '*node.exe*' } | Stop-Process
```

> **Важно:** Благодаря циклу `while($true) { node ./dist/server/entry.mjs; ... }` в `start_server.ps1`, при завершении процесса Node перезапуск происходит мгновенно, без разрыва цикла мониторинга.

* Агенту **ЗАПРЕЩАЕТСЯ** "гадать" или писать код по памяти.

## 7. Изоляция Изменений (Zero-Breakage Policy)
* Изменяя существующий компонент или логику (например, `Layout.astro` или `[id].astro`), агент должен минимизировать область изменений.
* Запрещается удалять существующие `id`, классы или функции, если это явно не требуется задачей, так как от них могут зависеть другие скрипты или тренажеры (iframe).

---

## 8. Защита Данных
* ИИ-агенту строго запрещается снимать комментарии с исключений в `.gitignore`. База данных `telemetry.db` и файлы с секретами (например, `.env`) **никогда** не должны попадать в индекс git.

## 9. Планирование и Пошаговая Реализация (Micro-planning)
* Получив объемную задачу (например, "Разработать урок"), агент **ОБЯЗАН** разбить ее на микро-шаги:
  1. Теоретический блок (`theory.md`) по учебнику Полякова (Zero-LaTeX, Zero-Leakage).
  2. Уровень 1 (`level1.astro`): манипуляции, Zero Multiple Choice.
  3. Уровень 2 (`level2.astro`): расчетные поля ввода, Anti-Paste.
  4. Уровень 3 (`level3.astro`): уникальный аркадный архетип, таймер, хардкор-сброс.
  5. **Обязательные тесты цифровых персон (`tests/*-student-personas.spec.js`):** проверка прохождения тренажеров виртуальными учениками (NOVICE, CARELESS, CHAOS, DILIGENT) через `StudentSimulator`.
* Не пытайтесь реализовать теорию и все уровни за один шаг. Составьте план и двигайтесь строго пошагово.
* Каждое логическое действие должно быть проверено перед переходом к следующему.

* Если агент сталкивается с непредвиденными трудностями, ошибками фреймворка, падением сборок или если задача не укладывается в архитектуру — **АГЕНТ ОБЯЗАН НЕМЕДЛЕННО ОСТАНОВИТЬСЯ**.
* Категорически запрещено пытаться "угадать" решение путем бесконечных итераций переписывания кода (галлюцинаций). Сделайте паузу, детально опишите проблему пользователю ПК и ждите его решения/разрешения.

## 12. Сетевые Особенности Тестирования на Windows и `BASE_URL`
* **Переменная `BASE_URL`:** Конфигурация `playwright.config.js` поддерживает переопределение хоста через `baseURL: process.env.BASE_URL || 'http://localhost:4321'`. При запуске тестов против тестового сервера передавайте переменную:
  ```powershell
  npx cross-env BASE_URL=http://localhost:3000 npx playwright test tests/my-test.spec.js
  ```
* **Запрет тестов на порту 8080:** Категорически запрещено направлять автотесты на боевой порт `8080`, чтобы не засорять боевую базу учащихся фейковыми телеметрическими событиями.
* **Обход системного прокси на Windows:**
  На Windows стандартные HTTP-клиенты (например, Python `urllib`) могут перенаправлять запросы к `127.0.0.1` или `localhost` через системный прокси, что приводит к ложной ошибке `HTTP 503 Service Unavailable`.
  В скриптах верификации всегда отключайте системный прокси:
  ```python
  import urllib.request
  opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
  resp = opener.open('http://127.0.0.1:8080/...')
  ```

## 13. Предрелизный Чек-лист Качества (Pre-PR Quality Checklist)
Перед отправкой ветки на GitHub и созданием Pull Request агент **ОБЯЗАН** выполнить строгую самопроверку:
1. **Zero Multiple Choice Policy:** Во всех трёх уровнях (`level1.astro`, `level2.astro`, `level3.astro`) полностью исключены тесты с выбором ответов.
2. **Zero-LaTeX Policy:** В файле `theory.md` нет служебных тегов LaTeX (`$`, `$$`, `\to`, `\times`, `\wedge`, `\vee`) — формулы оформлены чистым Unicode и тегами `<sub>`/`<sup>`.
3. **Исчерпывающие блоки «Дополнительная информация» (Zero-Leakage Policy):** В `theory.md` добавлены и детально проработаны разделы для Уровней 1, 2 и 3, дающие все знания для решения задач без раскрытия прямых ответов. Категорически запрещены совпадения дидактических примеров с тестовыми заданиями `levelX.astro`.
4. **Семантический визуал и прямое управление (Direct Manipulation & Zero Dead Canvas):**
   * В тренажерах отсутствуют пассивные декоративные экраны с дублированием данных из текста. Каждый графический элемент является источником уникальных данных (Data Source) либо органом прямого действия (Direct Surface).
   * Ученик манипулирует узлами схемы/поля непосредственно «на месте» (хитбоксы $\ge 48 \times 48\text{ px}$), а не через удаленные кнопочные пульты под экраном.
   * Анимации носят строго реактивный характер (150–350 мс) по событиям; непрерывные циклические фоновые 60 FPS эффекты исключены.
5. **100% зелёные автотесты Playwright:** Для урока создан тестовый сьют, и все тесты успешно пройдены.
6. **Безошибочная сборка:** Команда `npm run build` проходит за 1–2 секунды без предупреждений и ошибок.
7. **Чистый Shell:** Проверено отсутствие висящих фоновых задач (`manage_task list` возвращает 0 процессов).

## 14. Регламент Оформления Багов и Недоработок Уроков (Bug Reporting & Issue Tracking)

Когда при очном или дистанционном тестировании уроков с учащимися выявляются недоработки (ошибки валидации ответов, сбои процедурной генерации, опечатки/неточности в теории, баги в интерактивных механиках, проблемы с адаптивностью верстки на ноутбуках или сбои телеметрии), они фиксируются через **GitHub Issues**.

Это гарантирует сохранение полного контекста проблемы и позволяет легко взять исправление в работу человеку или ИИ-агенту.

### 14.1 Обязательная структура баг-репорта

Любой баг-репорт должен содержать четкую информацию без двусмысленностей:
1. **Точная локация проблемы:**
   * Учебный курс / когорта (например, `8-класс`, `10-класс_углубленный`, `11-класс_базовый`).
   * Номер и тема урока (например, `Урок 8 :: Логические операции`).
   * Компонент / файл: `Теория (theory.md)`, `Уровень 1 (level1.astro)`, `Уровень 2 (level2.astro)`, `Уровень 3 (level3.astro)` или серверная часть / дашборд.
2. **Шаги воспроизведения (Steps to Reproduce):**
   * Пошаговая цепочка действий, приведшая к сбою.
   * Конкретные сгенерированные входные данные (числа, логические выражения, состояние ленты/матрицы).
   * Введенный учащимся ответ или произведенное манипулятивное действие мышью.
3. **Фактический результат (Actual Result):**
   * Что именно пошло не так (ложный сброс фазы, зависание таймера, кнопка не реагирует, съехала верстка карточки, ошибка в консоли браузера).
4. **Ожидаемый результат (Expected Result):**
   * Корректное поведение системы согласно правилам курса и методике Полякова.
5. **Окружение и контекст:**
   * Режим (`Обычный` / `Хардкор`), разрешение экрана (`1920x1080`, `1366x768`), браузер (`Edge`, `Chrome`, `Яндекс.Браузер`).

### 14.2 Стандартный шаблон (Issue Template)

В репозитории настроен шаблон `.github/ISSUE_TEMPLATE/bug_report.md`. При оформлении через веб-интерфейс GitHub он подставляется автоматически. При ручном заполнении используйте следующий формат:

```markdown
### 1. Локация проблемы
- **Курс:** 8-класс
- **Урок:** Урок 8 :: Логические операции
- **Компонент:** Уровень 2 (`src/pages/tasks/8-класс/8/level2.astro`)

### 2. Шаги для воспроизведения
1. Открыть Уровень 2 (фаза 2 из 5).
2. Сгенерировано выражение: `not (1 and 0) or 0`.
3. Ввести ответ `1` и нажать Enter.

### 3. Фактический результат
```

### 14.4 Жизненный цикл исправления бага:

1. **Создание изолированного окружения:**
   ```powershell
   git worktree add -b fix/lesson-8-level2-validation D:\school-lms-dev
   cmd /c mklink /J "D:\school-lms-dev\node_modules" "D:\school-lms\node_modules"
   ```
2. **Регрессионный тест:** В папку `tests/` добавляется тест Playwright (или шаг в существующий тест урока), моделирующий проблемный случай.
3. **Исправление:** Правка кода в каталоге `D:\school-lms-dev`.
4. **Верификация:** Прогон автотестов (`npm run test:contracts` и `npx playwright test tests/...`).
5. **Создание PR со связкой тикета:**
   ```bash
   git commit -m "fix(content): корректный расчет дизъюнкции в Уроке 8 Уровня 2"
   git push -u origin fix/lesson-8-level2-validation
   gh pr create --title "fix: исправление валидации Урока 8 (Уровень 2)" --body "Closes #<НОМЕР_ISSUE>"
   ```
6. **Очистка Worktree:** Удаление временного рабочего дерева `D:\school-lms-dev` (см. Раздел 4).
