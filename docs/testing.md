# Автоматическое тестирование в School LMS (Testing Architecture & CI/CD)

В данном руководстве описана комплексная многоуровневая система автоматического тестирования интерактивных уроков и тренажеров платформы School LMS. Руководство написано понятным языком как для разработчиков, так и для методистов и преподавателей.

---

## 1. Что такое автоматические тесты и GitHub Actions (простыми словами)

### 1.1 Что такое автотесты?
Представьте, что перед каждым выпуском урока живому человеку нужно:
1. Зайти во все 3 уровня каждого урока.
2. Прочитать теорию и проверить, нет ли в формулах некрасивых спецсимволов вроде `$x_1$`.
3. Решить все задачи тренажеров, ввести правильные ответы и убедиться, что открылся экран победы.
4. Специально ошибиться в режиме хардкора и проверить, сработал ли сброс и перезагрузился ли тренажер.
5. Заглянуть в базу данных `telemetry.db` и проверить, записалась ли попытка и время прохождения.
6. Открыть урок на ноутбуке, планшете и большом мониторе, чтобы проверить, не съехала ли верстка.

Делать это вручную при каждом изменении долго и неизбежно ведет к человеческим ошибкам.
**Автотесты (Automated Tests)** — это специальный робот-программа (в нашем проекте — библиотека **Playwright**), которая открывает настоящий браузер за секунды, имитирует действия ученика с молниеносной скоростью, проверяет формулы, базу данных, делает скриншоты и гарантирует, что ничего не сломано.

### 1.2 Что такое автотесты на GitHub (GitHub Actions CI/CD)?
**GitHub** — это облачное хранилище исходного кода проекта.  
**GitHub Actions** — это встроенный в GitHub автоматический конвейер (CI/CD — *Continuous Integration / Continuous Deployment*):
* Каждый раз, когда разработчик или ИИ-агент отправляет изменения в репозиторий (`git push`) или создает запрос на объединение (`Pull Request`), GitHub бесплатно запускает виртуальный компьютер в облаке.
* Этот компьютер автоматически скачивает проект, собирает его (`npm run build`) и запускает весь набор наших тестов (`npx playwright test`).
* Если хотя бы один тест падает (например, формулы сломались или база данных не записала прогресс), GitHub ставит красный крестик ❌ и **блокирует попадание сломанного кода в основную ветку**.
* Если все тесты пройдены успешно, появляется зеленая галочка ✅. При этом отчеты, видеозаписи прохождения и скриншоты страниц автоматически сохраняются в виде архива (Artifacts), который можно скачать в один клик.

## 2. Пирамида тестирования School LMS

В нашем проекте внедрена современная **4-уровневая пирамида тестирования**:

```
           / \
          /   \     Уровень 3: Сквозные E2E & Визуальные тесты
         / E2E \    (Полное прохождение, хардкор-сброс, таймеры, скриншоты)
        /-------\
       /         \    Уровень 2: Контрактные тесты данных и API
      /  Data &   \   (Схема SQLite, запись телеметрии, безопасность)
     /  Telemetry  \
    /---------------\
   /                 \  Уровень 1.5: Контракты процедурной генерации и UX
  / Procedural & UX   \ (Инварианты формул, робастность ввода, BFS графов)
 /---------------------\
/                       \ Уровень 1: Архитектурный линтинг учебного плана
/    Curriculum Lint    \ (Проверка теории, запрет сырого LaTeX $, 3 уровня)
/-------------------------\
```

### Уровень 1: Архитектурный линтинг контента (`curriculum-lint.spec.js`)
* **Скорость выполнения:** менее 0.1 сек.
* **Что проверяет:**
  1. Наличие файла `theory.md` и ключевых терминов школьной программы.
  2. **Zero-LaTeX Policy:** автоматический запрет на сырые разделители `$ ... $` и `$$ ... $$` в markdown. Формулы обязаны быть оформлены в чистом типографском виде с HTML-тегами `<sub>`, `<sup>` и Unicode-символами (`λ`, `α`, `→`).
  3. Наличие файлов `level1.astro`, `level2.astro`, `level3.astro`.
  4. Использование обязательного компонента `<TaskLayout>` с атрибутами метаданных.
  5. Отсутствие запрещенных тегов `<style>` (гарантия использования утилит Tailwind CSS).

### Уровень 1.5: Контракты процедурной генерации, математических инвариантов и робастности интерфейса (`procedural-integrity.spec.js`, `procedural-contracts.js`)
* **Скорость выполнения:** 1-3 сек.
* **Библиотека переиспользуемых контрактов:** `tests/procedural-contracts.js`.
* **Что проверяет (5 универсальных контрактов):**
  1. **Контракт 1: Математические инварианты процедурной генерации (`verifyMathInvariants`):**
     * Проверка равенства эталонного математического решения и ключа валидатора тренажера.
     * Защита от ошибок вещественного деления и плавающей точки (`0.1 + 0.2`).
     * Проверка дельт формул (например, разница сжатия `P = (D - B) / D * 100` с фиксированным округлением `Math.round(P * 10) / 10`).
     * Предотвращение дробных нецелых параметров в контекстах дискретных объектов (символы, байты).
  2. **Контракт 2: Нечеткая устойчивость (Fuzzing) пользовательского ввода (`generateInputMutations`):**
     * Поддержка русской десятичной запятой `,` и международной точки `.` (запрет на использование нативного `<input type="number">`, блокирующего запятую; обязательное использование `type="text" inputmode="decimal"`).
     * Толерантность к знаку процента `%`, случайным пробелам по краям и внутри строки.
     * Нечувствительность к регистру (`CAPS` / `lower`) и грамматическим падежным окончаниям (лемматизация).
     * Распознавание синонимов из школьного тезауруса (например, `натурная` / `материальная`).
  3. **Контракт 3: Гарантированная разрешимость и отсутствие тупиков графов/матриц (`verifyMatrixProceduralSolvability`):**
     * Монте-Карло симуляция (100+ случайных итераций генератора).
     * BFS-поиск гарантированного маршрута от старта к цели.
     * Валидация отсутствия ловушек-дистракторов (ситуаций, когда ложный токен полностью блокирует прохождение).
     * Запрет коллизий дублирования ключевых токенов на соседних клетках от старта.
  4. **Контракт 4: Онтологический линтер школьного тезауруса (`lintOntologySequence`):**
     * Статический и динамический контроль соответствия классификации ФГОС.
     * Предотвращение смешивания взаимоисключающих понятийных категорий (например, классификация моделей: «натурная (материальная)» строго отделена от «информационной: образной / знаковой / смешанной»).
  5. **Контракт 5: Надежность интерактивных манипуляторов (Click-to-Move / Drag-and-Drop):**
     * Тестирование кликов и перемещения не только по пустому слоту, но и по вложенным элементам (бейджи, заголовки карточек, счетчики).
     * Предотвращение блокировки всплытия событий (`stopPropagation`) внутри карточек.

### Уровень 2: Целостность базы данных, API телеметрии и дашборда учителя (`telemetry-contract.spec.js`, `teacher-dashboard.spec.js`)
* **Скорость выполнения:** около 1-2 сек.
* **Что проверяет:**
  1. **Нормализованная схема SQLite:** наличие полей `student_class`, `course_slug`, `lesson_id`, `level_number`, а также композитных индексов `idx_telemetry_student_cohort` и `idx_telemetry_course_lesson`.
  2. **Контракт API телеметрии:** отправку событий завершения уровня (`level_complete`) и хардкор-сброса (`hardcore_reset`) через `POST /api/telemetry` с корректной записью когорты и параметров урока.
  3. **Защита от некорректных данных:** возврат HTTP 400 / 403 при невалидном Content-Type или поврежденных типах данных.
  4. **API аналитики учителя (`GET /api/teacher/stats`):** точность агрегации KPI, фильтрацию по нескольким классам через запятую (`class=10-класс_углубленный,11-класс_углубленный`), фильтрацию по курсу (`course=8-класс`), исключение тестовых профилей и корректную атрибуцию когорт в межкурсовых соревнованиях.
  5. **Интерфейс дашборда и кабинета:** динамическое обновление селектора уроков при выборе курса, мульти-сортировка колонок (Ctrl/Shift) и переключение каталога в кабинете `/courses` без сброса профиля учащегося.

### Уровень 2.5: Эмуляция поведения ученика и цифровые персоны (`student-simulator.js`, `*-student-personas.spec.js`)
* **Скорость выполнения:** 3–7 сек (до 30 сек на полный набор).
* **Модули:**
  - `tests/student-simulator.js` ([`StudentSimulator`](file:///D:/school-lms-dev/tests/student-simulator.js)) — базовый движок симуляции поведения для стандартных полей ввода, кнопок, сеток и Drag-and-Drop.
  - `tests/student-writer-simulator.js` ([`StudentWriterSimulator`](file:///D:/school-lms-dev/tests/student-writer-simulator.js)) — специализированный движок для текстовых процессоров (LibreOffice Writer, Jodit WYSIWYG, ОГЭ 13.2).
* **Цель:** Полное исключение эффекта «всезнающего автора» (white-box bias), когда тест решал задачу через бэкдор-хуки (`window.__testState`) или точное знание приватных селекторов генератора.

> [!IMPORTANT]
> ### 🚨 Глобальный регламент: Обязательное создание тестов персон для КАЖДОГО урока
> При создании или доработке **каждого урока** разработчик/ИИ-агент **ОБЯЗАН** создать файл поведенческих тестов:
> `tests/lesson<id>-grade<class>-student-personas.spec.js` (или `tests/lesson<class>-<id>-student-personas.spec.js`)
> и зарегистрировать его в скрипте `"test:personas"` в `package.json`.
> 
> Тест обязан эмулировать реальное прохождение тренажеров учащимися через `StudentSimulator` по всем трем уровням:
> 1. **Уровень 1 (Манипуляции / Drag-and-Drop / Сортировка):**
>    - `Persona NOVICE:` намеренно совершает типовую ошибку (выбирает дистрактор / путает порядок) → фиксирует появление алерта `#feedback-box` и инкремент счетчика `#attempts-display` → выдерживает когнитивную паузу → очищает форму и успешно решает задание.
>    - `Persona CHAOS:` производит серию быстрых спам-кликов по кнопкам сброса, слотам и палитре, проверяя отсутствие рассинхронизации DOM и зависаний.
> 2. **Уровень 2 (Аналитический расчет / Поля ввода):**
>    - `Persona CARELESS:` вводит числа с пробелами по краям (`" 12.5 "`), использует русскую запятую вместо точки (`"3,14"`), отправляет форму нажатием клавиши `Enter` в инпуте → проверяется толерантность парсинга полей ввода.
>    - `Persona NOVICE:` вводит некорректное/пустое значение → убеждается в понятности ошибки → вводит верный математический расчет.
>    - `Persona CHAOS:` проверяет блокировку вставки (Anti-Paste Policy).
> 3. **Уровень 3 (Аркадный «Финальный босс»):**
>    - `Persona NOVICE:` совершает ошибку в первой волне (промах тайминга / неверный переключатель) → проверяет срабатывание сирены аварии, отправку события `hardcore_reset` в телеметрию и автоматический сброс на Волну 1.
>    - `Persona DILIGENT:` честно решает волны исключительно по видимым семантическим элементам DOM («черный ящик»), синхронизируясь с ритмом или физикой конвейера.

* **Что проверяет (4 цифровые персоны учащихся):**
  1. **Persona `NOVICE` (Новичок):** Впервые видит задание, делает паузы на чтение условий (`cognitivePause`), ошибается на дидактических ловушках/дистракторах. Тест проверяет, что сообщение об ошибке понятно, попытка зафиксирована, процедурная перегенерация происходит штатно, а последующая правильная попытка разблокирует прогресс.
  2. **Persona `CARELESS` (Торопливый / Невнимательный):** Пытается отправить форму пустой, вводит числа с пробелами по краям, русскую запятую вместо точки (`3,14`), отправляет ответ нажатием клавиши `Enter` в поле ввода. В текстовом редакторе путает кириллические/латинские буквы-двойники (омоглифы С/C, А/A, о/o) и оставляет лишние пробелы.
  3. **Persona `CHAOS` (Хаос / Исследователь):** Тестирует устойчивость интерфейса к спам-кликам (debounce), двойным кликам, кликам по пустым гнездам, спаму кнопок тулбара и попыткам запрещенной вставки (Anti-Paste Policy).
  4. **Persona `DILIGENT` (Вдумчивый ученик / Black-Box):** Решает задание исключительно по видимым текстовым формулировкам и семантическим элементам в DOM, без обращения к `window.__testState` или скрытым техническим ID токенов.

#### Особенности тестирования текстовых процессоров и WYSIWYG (`StudentWriterSimulator`):
* **Запрет на `.fill()` в `contenteditable`:** Метод Playwright `.fill()` не работает с WYSIWYG-контейнерами Jodit. Симулятор использует реалистичную печать с клавиатурными задержками (`page.keyboard.type`) и эмуляцию перемещения каретки.
* **Выделение текста через DOM Range API:** Метод `selectText(word)` находит текстовые узлы внутри документа и создает честный `Range` в окне браузера перед нажатием кнопок форматирования (`#btn-bold`, `#btn-italic`, `#btn-underline`).
* **Ловушка залипания каретки (Zero Caret Trapping):** Метод `typeFormulaWithSubSup('H', '2', 'sub', 'O')` проверяет, что при повторном клике на кнопку индекса каретка корректно выходит за пределы тега `<sub>`/`<sup>` и следующий символ не наследует индексное оформление.
* **Очистка невидимых Unicode-артефактов:** Jodit внедряет невидимые символы нулевой ширины (`\u200B`, `\uFEFF`). Для точной проверки разметки используется метод `getCleanEditorHTML()`.
* **Педагогические ловушки новичка:**
  - `simulateSpaceIndentTrap()`: попытка сделать красную строку 5 пробелами вместо настройки абзаца (детектор ОГЭ 13.2 блокирует такой документ).
  - `simulateHyphenTrap()`: ввод дефиса `-` вместо типографского тире `—`.
* **Настройка геометрии документа:** Эмуляция интерактивного клика по маркеру линейки LibreOffice (`setIndentViaRuler`) и вызова модального окна `Формат → Абзац...` (`configureParagraphViaDialog`).

* **Команда запуска всех тестов персон:**
  ```bash
  npm run test:personas
  ```

### Уровень 2.7: Автоматическая калибровка и оценка сложности (Difficulty Benchmarking Engine)
* **Файлы:** 	ests/difficulty-benchmarker.js ([DifficultyBenchmarker](file:///D:/school-lms-dev/tests/difficulty-benchmarker.js)), 	ests/difficulty-benchmarker.spec.js.
* **Скорость выполнения:** менее 0.5 сек.
* **Что проверяет:**
  1. **Индекс Когнитивной Сложности (CCS 1–10):** программный расчет формулы CCS = F_depth + F_memory + F_search + F_inversion + F_stress - S_scaffolding для каждой фазы урока.
  2. **Возрастные коридоры параллелей (Grade Corridors):** автоматический контроль того, что задания не выходят за рамки возрастной когнитивной емкости (7 класс: [2; 5], 8 класс: [3; 6], 9 класс: [4; 7], 10–11 базовый: [4; 7], 10–11 технологический: [5; 10]).
  3. **Золотая Пилообразная Кривая (Sawtooth 2-1-2 на Уровне 2):** строгая проверка пятифазного ритма:
     * P_1 ≤ P_2 ≤ P_3 (постепенное восхождение к первому пику);
     * P_4 < P_3 (**ОБЯЗАТЕЛЬНЫЙ СПАД — Долина консолидации** памяти перед кульминацией);
     * P_5 ≥ P_3 (Финальная кульминация с граничными случаями).
  4. **Детекторы Фальшивой сложности (Fake Difficulty Linter):**
     * *Pixel Hunting Guard:* автоматический аудит oundingBox интерактивных элементов (запрет зон клика меньше 36×36 px по закону Фиттса).
     * *Arithmetic Grind Guard:* выявление негуманных вычислений (многозначные числа вне степеней двойки).
     * *Flat Plateau Guard:* блокировка монотонных одинаковых фаз без дидактического прогресса.
  5. **Визуализация кривой в консоли:** генерация ASCII-отчета с прогресс-барами сложности по каждой фазе урока и фиксацией замеренной задержки (latencyMs).

* **Команда запуска тестов калибровки сложности:**
  `ash
  npm run test:difficulty
  `

### Уровень 3: Сквозные тесты прохождения, хардкора и визуального контроля
* **Файлы:** `lesson11-20-level1.spec.js`, `lesson11-20-level2.spec.js`, `lesson11-20-level3.spec.js`, `lesson20-visual-ux.spec.js`.
* **Что проверяет:**
  1. **Успешное прохождение (Normal Flow):** алгоритмический бот вычисляет верные ответы на основе процедурной генерации, заполняет формы и проверяет экран победы.
  2. **Хардкор-режим (Hardcore Reset):** намеренная ошибка с проверкой перехвата диалогового окна (`dialog.accept()`), полного сброса фазы и генерации новых данных.
  3. **Таймеры и аркадная механика:** в Уровне 3 проверяется убывание локального таймера, статус волн и реакция на тайм-аут.
  4. **Доступность и клавиатура:** проверяется ввод ответов и отправка по нажатию клавиши `Enter`.
  5. **Адаптивность и скриншоты:** рендеринг в разрешениях 1920x1080 (Desktop), 1366x768 (Laptop) и сохранение скриншотов в папку `scratch/`.

## 3. Конфигурация GitHub Actions (`.github/workflows/test.yml`)

В репозитории настроен автоматический рабочий процесс:

```yaml
name: School LMS Automated Testing & CI

on:
  push:
    branches: [ main, 'content/**', 'feature/**' ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
        env:
          CI: true
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
```

В файле `playwright.config.js` автоматически определяется окружение:
* В облаке GitHub Actions запускается чистый Chromium без зависимостей от системного Edge.
* На локальных компьютерах разработчиков под Windows используется системный Edge (`msedge`).
* В случае падения теста скриншот сбоя и трассировка событий автоматически сохраняются.

## 4. Команды запуска тестов

Для удобства добавлены сценарии в `package.json`:

```bash
# 1. Запустить быстрые тесты контрактов (линтинг теории и базы данных телеметрии)
npm run test:contracts

# 2. Запустить универсальные тесты процедурной генерации, математических инвариантов и UX
npm run test:integrity

# 3. Запустить полный цикл тестов для конкретного Урока 20 (все 3 уровня + визуальный UX)
npm run test:lesson20

# 4. Запустить полный набор всех автотестов проекта
npm test

# 5. Открыть интерактивный графический интерфейс Playwright для отладки
npx playwright test --ui
```

## 5. Памятка для агентов и разработчиков

1. При добавлении нового урока **обязательно** создавайте тест `tests/lessonXX-*.spec.js`.
2. Для процедурно-генерируемых заданий подключайте контракты из `tests/procedural-contracts.js` и проверяйте их через `npm run test:integrity`.
3. Поле ввода чисел и процентов **никогда не должно быть** `<input type="number">`, так как браузер блокирует русскую запятую `,` и знак `%`. Используйте `type="text" inputmode="decimal"` с нормализацией `.replace('%', '').replace(',', '.').trim()`.
4. В интерактивных механиках с перемещением элементов (Click-to-Move, Drag-and-Drop) используйте делегирование событий и никогда не блокируйте всплытие (`stopPropagation`) на внутренних бейджах и карточках.
5. Перед коммитом запускайте `npm run test:contracts` и `npm run test:integrity`.
6. Сохраняйте скриншоты в папку `scratch/` для визуального контроля и удаляйте временные файлы перед отправкой Pull Request.
7. Никогда не используйте сырой LaTeX синтаксис в `theory.md` — за этим следит автоматический линтер.
8. **Обязательное создание тестов цифровых персон:** Для КАЖДОГО создаваемого урока ОБЯЗАТЕЛЬНО создавайте файл `tests/lesson<id>-grade<class>-student-personas.spec.js`, подключающий `StudentSimulator` и проверяющий поведение 4 персон (NOVICE, CARELESS, CHAOS, DILIGENT). Обязательно регистрируйте новый файл в `package.json` (`test:personas`).
