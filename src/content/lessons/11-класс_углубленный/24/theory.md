# ⚙️ Алгоритмически неразрешимые задачи. Задача останова. Невозможность автоматической отладки программ (по К.Ю. Полякову)

## 1. Понятие алгоритмической неразрешимости массовых проблем 📜

В базовом курсе информатики и на начальных этапах изучения программирования складывается естественное впечатление, что для любой четко сформулированной математической или информационной задачи можно составить алгоритм, а единственное ограничение заключается лишь в мастерстве программиста и быстродействии современных компьютеров.

Однако одно из величайших открытий теоретической информатики XX века состоит в доказательстве фундаментального факта:
> 📌 **Существуют точно поставленные задачи, для которых алгоритма решения не существует в принципе.**
> Иными словами, невозможность их решения обусловлена не технической отсталостью или нехваткой памяти, а **объективными законами математической логики**.

```
                  ┌──────────────────────────────────────────────────┐
                  │          ВСЕ МАТЕМАТИЧЕСКИЕ ЗАДАЧИ               │
                  │                                                  │
                  │   ┌──────────────────────────────────────────┐   │
                  │   │      АЛГОРИТМИЧЕСКИ РАЗРЕШИМЫЕ           │   │
                  │   │   (Сортировка, НОД, поиск пути,          │   │
                  │   │    умножение матриц, синтаксис)          │   │
                  │   └──────────────────────────────────────────┘   │
                  │                                                  │
                  │   ┌──────────────────────────────────────────┐   │
                  │   │     АЛГОРИТМИЧЕСКИ НЕРАЗРЕШИМЫЕ          │   │
                  │   │   (Задача останова, теорема Райса,       │   │
                  │   │    10-я проблема Гильберта, ПСП Поста,   │   │
                  │   │    идеальная отладка и верификация)      │   │
                  │   └──────────────────────────────────────────┘   │
                  └──────────────────────────────────────────────────┘
```

---

### 1.1 Что такое массовая алгоритмическая проблема?
В теории алгоритмов под **массовой проблемой** (массовой задачей) понимается требование найти единый общий метод решения не для одного изолированного примера, а для **бесконечного класса однотипных задач**, различающихся исходными данными (свойство *массовости* алгоритма).

* **Пример разрешимой массовой проблемы:** «Даны два произвольных натуральных числа a и b. Найти их наибольший общий делитель (НОД)».
  * Для любого бесконечного множества пар (a, b) алгоритм Евклида гарантированно дает верный ответ за конечное число шагов. Задача **алгоритмически разрешима**.
* **Пример проблемы разрешения (Decision Problem):** Массовая задача, ответом на которую для любого входного набора данных может быть только одно из двух логических значений: **«Да» (Истина / 1)** или **«Нет» (Ложь / 0)**.

---

### 1.2 Частные алгоритмы против универсального алгоритма
Очень важно различать возможность решить *частный случай* задачи и существование *универсального алгоритма*:
* Если дана конкретная программа из трех строк:
  ```python
  x = 5
  y = 10
  print(x + y)
  ```
  любой школьник легко определит, что эта программа завершится успешно. Для этого конкретного частного случая ответ известен.
* Однако **массовая проблема** требует создать **единую программу-анализатор**, которая сможет принять на вход **абсолютно любую** произвольную программу любой сложности (с сотнями миллионов строк, сложнейшими рекурсиями, динамическим выделением памяти) и для каждого возможного случая безошибочно выдать верный ответ за конечное время.

> 💡 **Определение:** Массовая алгоритмическая задача называется **алгоритмически неразрешимой**, если математически доказано, что **не существует единого детерминированного алгоритма**, способного решить ее за конечное число шагов для **всех** допустимых наборов входных данных.

---

### 1.3 Зачем понадобилась формализация алгоритма?
Как отмечалось при изучении машины Тьюринга, чтобы доказать существование алгоритма, достаточно его разработать и продемонстрировать. Но чтобы строго доказать, что алгоритма **не существует вообще**, интуитивного определения («понятная последовательность команд») недостаточно. Требовалось строго очертить границы того, что вычислимо в принципе. 

Благодаря тезису Чёрча — Тьюринга было установлено:
* Если некоторая задача не может быть решена машиной Тьюринга, она **не может быть решена ни на каком компьютере**, ни на каком языке программирования настоящего и будущего.

## 2. Проблема останова (The Halting Problem) 🛑

Центральной и исторически первой алгоритмически неразрешимой задачей, сформулированной и исследованной Аланом Тьюрингом в 1936 году, стала **проблема остановки** (задача останова).

```
               Входные данные:
    ┌───────────────────────────────────┐
    │  Исходный текст программы P       │
    │  Входные данные программы X       │
    └─────────────────┬─────────────────┘
                      │
                      ▼
    ┌───────────────────────────────────┐
    │    Гипотетический универсальный   │
    │         анализатор H(P, X)        │
    └─────────────────┬─────────────────┘
                      │
           ┌──────────┴──────────┐
           ▼                     ▼
     ОТВЕТ: "ДА"           ОТВЕТ: "НЕТ"
   (P(X) завершится      (P(X) никогда не
    за конечное время)    завершится, зациклится)
```

### 2.1 Формулировка проблемы останова
Пусть у нас имеется:
1. Текст некоторой программы `P` (записанный на любом языке программирования или в виде таблицы переходов машины Тьюринга).
2. Набор исходных данных `X`, передаваемых этой программе на вход.

При запуске программы `P` на данных `X` возможны только два исхода:
1. Программа выполнит конечное число инструкций и **завершит работу (штатно остановится)**, выдав результат или сообщение об ошибке.
2. Программа войдет в **бесконечный цикл (зациклится)** и никогда не остановится самостоятельно.

> ❓ **Формулировка задачи:** Возможно ли разработать универсальный алгоритм (функцию `H(P, X)`), который, принимая на вход текст произвольной программы `P` и ее входные данные `X`, **всегда за конечное время** выдает точный ответ: завершится ли выполнение `P(X)` или зациклится?

---

### 2.2 Почему нельзя просто запустить программу и подождать?
Наивное предложение: *«Давайте просто запустим программу `P(X)` на виртуальной машине или в эмуляторе и посмотрим, что произойдет!»*

В чем состоит фундаментальный тупик такого подхода?
1. Если программа завершилась через 5 секунд — мы знаем, что она останавливается, и выдаем ответ `True`.
2. Если программа работает уже 1 час, 1 год или 100 лет — **мы не можем знать, зациклилась ли она навсегда, или ей требуется еще одна миллисекунда для завершения работы!**
3. Анализатор, который просто ждет завершения проверяемой программы, сам зависнет на бесконечный срок, если программа `P(X)` зациклилась. Тем самым он нарушит базовое требование к алгоритмам — свойство результативности (завершаться за конечное число шагов при любых входах).

Следовательно, гипотетический анализатор `H(P, X)` обязан **не моделировать слепо выполнение программы до бесконечности**, а исследовать ее текст аналитически (статически) и выносить безошибочный вердикт за конечное число шагов.

## 3. Строгое доказательство теоремы Тьюринга методом от противного 🧠

Докажем теорему Алана Тьюринга о неразрешимости проблемы останова строгим математическим методом от противного. Доказательство использует логическую конструкцию, родственную диагональному методу Георга Кантора и знаменитому парадоксу Рассела.

### Шаг 1. Предположение от противного
Предположим, что такой универсальный анализатор существует. Назовем его функцией `H(program_code, input_data)`:

```python
def H(program_code: str, input_data: str) -> bool:
    """
    Гипотетический идеальный анализатор останова.
    Возвращает True, если программа program_code(input_data) останавливается.
    Возвращает False, если программа program_code(input_data) зацикливается.
    ГАРАНТИРОВАННО завершает свою работу за конечное время при любых входах.
    """
```

Так как любая программа представляет собой просто текстовую строку (последовательность символов в кодировке UTF-8 или ASCII), программу можно передавать другой программе в качестве входных данных. В частности, программу можно передать в качестве входных данных **самой себе** (точно так же, как компилятор C++ может компилировать исходный код собственного компилятора, а линтер Python может анализировать код самого линтера).

Вызов `H(P, P)` означает: *«Остановится ли программа P, если ей на вход подать текст ее собственного исходного кода?»*

---

### Шаг 2. Построение парадоксальной программы D (Диагональная конструкция)
Опираясь на гипотетическую функцию `H`, сконструируем новую вспомогательную программу `D` (от слова *Diagonal* или *Disruptor*). 

Программа `D` принимает на вход исходный код произвольной программы `P`, вызывает функцию `H(P, P)` и затем поступает **строго противоположным образом**:

```python
def D(P: str):
    # Анализируем поведение программы P на собственном исходном коде:
    halts = H(P, P)
    
    if halts == True:
        # Если анализатор H предсказал, что P(P) остановится,
        # программа D НАМЕРЕННО входит в бесконечный цикл!
        while True:
            pass
    else:
        # Если анализатор H предсказал, что P(P) зациклится,
        # программа D НЕМЕДЛЕННО успешно завершает работу!
        return
```

Логика программы `D` кристально прозрачна:
* Если `P(P)` завершается → `D(P)` зависает в бесконечном цикле `while True`.
* Если `P(P)` зацикливается → `D(P)` моментально завершает работу через `return`.

Программа `D` абсолютно корректна с точки зрения синтаксиса любого тьюринг-полного языка программирования.

---

### Шаг 3. Критический шаг — подача программы D самой себе: вызов D(D)
Теперь передадим программе `D` в качестве аргумента ее собственный исходный код. Что произойдет при вызове `D(D)`?

Рассмотрим два единственно возможных исхода:

#### Исход А: Предположим, что вызов D(D) завершается за конечное время
1. Если выполнение `D(D)` завершается, то идеальный анализатор `H`, вызванный внутри с аргументами `(D, D)`, обязан вернуть истину:
   `H(D, D) == True`.
2. Но посмотрим на код функции `D`! При условии `halts == True` управление попадает в ветку `if`:
   ```python
   while True:
       pass
   ```
   то есть программа `D` входит в бесконечный цикл и **никогда не завершается**!
3. **Противоречие!** Мы предположили, что `D(D)` завершается, а получили, что `D(D)` зацикливается.

#### Исход Б: Предположим, что вызов D(D) зацикливается (не завершается)
1. Если выполнение `D(D)` никогда не завершается, то идеальный анализатор `H` обязан вернуть ложь:
   `H(D, D) == False`.
2. Но смотрим на код функции `D`! При условии `halts == False` управление переходит в ветку `else`:
   ```python
   return
   ```
   то есть программа `D` немедленно выходит и **успешно завершает работу за конечное время**!
3. **Снова противоречие!** Мы предположили, что `D(D)` зацикливается, а получили, что `D(D)` завершается.

---

### Шаг 4. Заключение и вывод
Мы получили неустранимое логическое противоречие в обоих мыслимых случаях:
```
  D(D) завершается  ⟺  D(D) зацикливается
```
Ни одна программа не может одновременно завершаться и зацикливаться.

Где кроется ошибка в наших рассуждениях? 
* Конструкция условного оператора `if-else` в `D` логически безупречна.
* Организация бесконечного цикла `while True` математически законна.
* Подача текста программы самой себе на вход — стандартная операция Computer Science.

Единственное неверное допущение во всей логической цепочке — **само предположение о принципиальной возможности существования функции `H`**!

> 🏆 **Теорема Тьюринга (1936):**
> **Универсального алгоритма для решения проблемы остановки не существует. Задача останова алгоритмически неразрешима.**

---

### 3.4 Связь с классическими логическими парадоксами
Доказательство Тьюринга имеет глубочайшие философские и математические корни:
1. **Парадокс лжеца:** Утверждение *«Данное высказывание ложно»*. Если оно истинно, то оно ложно; если оно ложно, то оно истинно.
2. **Парадокс брадобрея (Бертран Рассел, 1901):** В деревне брадобрей бреет всех тех и только тех жителей, которые не бреются сами. Бреет ли брадобрей самого себя? Если бреет — не должен; если не бреет — обязан.
3. **Теорема Гёделя о неполноте (Курт Гёдель, 1931):** В любой непротиворечивой формальной математической системе, содержащей арифметику, существуют истинные утверждения, которые невозможно доказать средствами самой этой системы.
4. **Диагональный метод Кантора (Георг Кантор, 1891):** Доказательство несчетности множества действительных чисел путем построения числа на диагонали таблицы, отличающегося от каждого числа в строке хотя бы одним разрядом.

Программа Тьюринга `D` действует точно так же: она инвертирует «диагональный элемент» таблицы вычислений `H(P<sub>i</sub>, P<sub>i</sub>)`.

## 4. Теорема Райса: Фундаментальное обобщение проблемы останова ⚖️

Некоторые программисты могут подумать: *«Хорошо, проблему остановки решить нельзя. Но ведь можно проверить другие полезные свойства программ? Например, выяснить, выдает ли функция число 0, или не содержит ли она ошибок деления на ноль?»*

Ответ на этот вопрос в 1953 году дал американский математик **Генри Гордон Райс (Henry Gordon Rice)**. Его теорема нанесла сокрушительный удар по мечтам об универсальных анализаторах программ.

```
       ┌─────────────────────────────────────────────────────────────┐
       │                   СВОЙСТВА ПРОГРАММЫ                        │
       ├──────────────────────────────┬──────────────────────────────┤
       │   СИНТАКСИЧЕСКИЕ СВОЙСТВА    │    СЕМАНТИЧЕСКИЕ СВОЙСТВА    │
       │    (Свойства самого кода)    │   (Свойства поведения кода)  │
       ├──────────────────────────────┼──────────────────────────────┤
       │ • Длина текста программы     │ • Выдает ли программа ответ? │
       │ • Наличие ключевого слова for│ • Равен ли результат числу 42│
       │ • Количество переменных      │ • Произойдет ли деление на 0?│
       │ • Парность круглых скобок    │ • Завершится ли выполнение?  │
       ├──────────────────────────────┼──────────────────────────────┤
       │    АЛГОРИТМИЧЕСКИ РАЗРЕШИМЫ  │  АЛГОРИТМИЧЕСКИ НЕРАЗРЕШИМЫ  │
       │ (Парсеры, регулярные выраж.) │      (ТЕОРЕМА РАЙСА!)        │
       └──────────────────────────────┴──────────────────────────────┘
```

### 4.1 Формулировка теоремы Райса
Сначала введем строгое определение:
* Свойство программы называется **семантическим**, если оно относится не к форме записи исходного кода, а к поведению функции, которую эта программа вычисляет (то есть к соответствию «входные данные → выходные данные»). Если две программы `P<sub>1</sub>` и `P<sub>2</sub>` написаны совершенно по-разному, но для одинаковых входов всегда выдают одинаковые выходы, они обладают одинаковыми семантическими свойствами.
* Свойство называется **тривиальным**, если им обладают либо **все** вычислимые функции без исключения, либо **ни одна** функция (например, свойство «быть программой» тривиально, так как им обладают все программы).

> 📌 **Теорема Райса (1953):**
> **Всякое нетривиальное семантическое свойство программ алгоритмически неразрешимо.**

---

### 4.2 Следствия теоремы Райса
Из теоремы Райса следует, что **не существует и не может существовать алгоритма**, способного по тексту произвольной программы определить:
1. Завершается ли программа хотя бы на одном наборе входных данных.
2. Вычисляет ли программа функцию f(x) = x<sup>2</sup>.
3. Выведет ли программа когда-нибудь на печать строку `"Hello, World!"`.
4. Содержит ли программа недостижимый код («мертвый код», Dead Code).
5. Возникнет ли в процессе вычислений переполнение буфера памяти (Buffer Overflow) или разыменование нулевого указателя (Null Pointer Dereference).
6. Являются ли две произвольные программы `A` и `B` функционально эквивалентными (делают ли они одно и то же).

Любая попытка создать идеальный универсальный детектор для любого из этих вопросов немедленно наталкивается на сведение к проблеме останова!

## 5. Невозможность автоматической отладки программ и идеальной верификации 🛠️

Из теорем Тьюринга и Райса вытекают фундаментальные прикладные следствия для всей индустрии разработки программного обеспечения.

```
       ┌────────────────────────────────────────────────────────┐
```

### 5.1 Почему невозможно создать «Идеальный отладчик» (Perfect Debugger)?
Каждый начинающий разработчик мечтает об утилите:
* Нажимаем кнопку `Проверить логику программы`.
* Утилита анализирует код и сообщает: *«В строке 42 цикл никогда не завершится при отрицательных n»* или *«Программа работает идеально во всех 100% случаев»*.

Почему создание такой утилиты теоретически невозможно?
* Чтобы установить, есть ли в программе бесконечный цикл, утилита обязана решить проблему остановки Тьюринга.
* Чтобы проверить, соответствует ли поведение программы техническому заданию, утилита обязана решить проблему семантической эквивалентности (теорема Райса).
* Следовательно: **автоматическая идеальная отладка программ в общем виде невозможна**.

### 5.2 Статический анализ кода (Линтеры и SAST) в реальной практике
Если идеальный анализ невозможен, как работают современные инструменты разработки:
* Линтеры и анализаторы кода: **ESLint, Pylint, Flake8, SonarQube, Clang-Tidy, Coverity**;
* Компиляторы языков: **gcc, clang, rustc, javac**?

Все реальные анализаторы используют **приближенные методы, эвристики и абстрактную интерпретацию**. Из-за теоретической неразрешимости они вынуждены балансировать между двумя неизбежными типами ошибок:

1. **Ложноположительные срабатывания (False Positives / Ошибка I рода):**
   * Анализатор выдает предупреждение об ошибке или зависании там, где код на самом деле абсолютно корректен. Разработчику приходится ставить комментарии подавления (`# noqa`, `// nolint`).
2. **Ложноотрицательные срабатывания (False Negatives / Ошибка II рода):**
   * Анализатор боится беспокоить программиста ложными тревогами, пропускает сложный случай взаимосвязи переменных, в результате чего критический баг попадает в продакшн.

> 💡 **Принцип:** Никакой статический анализатор кода не может быть одновременно **полным** (находить 100% всех возможных дефектов) и **точным** (никогда не давать ложных срабатываний) на произвольных программах.

### 5.3 Информационная безопасность: Теорема Фреда Коэна и антивирусное ПО
В 1984 году американский ученый **Фред Коэн (Fred Cohen)** в своей пионерской диссертации о компьютерных вирусах доказал фундаментальную теорему информационной безопасности:

> 📌 **Теорема Коэна (1984):**
> **Не существует алгоритма, который способен для произвольной программы безошибочно определить, является ли она компьютерным вирусом (вредоносной программой).**

*Доказательство:* Вредоносность — это семантическое свойство поведения программы. По теореме Райса оно алгоритмически неразрешимо. Хакер всегда может сконструировать вирус, выполнение которого зависит от решения проблемы останова некоторого сложного кода:
* Вирус говорит: *«Я запущу шифрование диска тогда и только тогда, когда программа P(X) завершится»*.
* Чтобы антивирус определил вредоносность до запуска файла, он обязан предсказать поведение `P(X)`.

Именно поэтому современная индустрия антивирусов (Kaspersky, Windows Defender, CrowdStrike) использует эшелонированный комплекс приближенных механизмов:
* **Сигнатурный анализ:** поиск совпадения байт-кода с базой уже известных зловредов (быстро, но бессильно против новых вирусов);
* **Эвристический анализ:** поиск подозрительных API-вызовов (инъекция в память, перехват клавиатуры);
* **Поведенческий анализ в песочнице (Sandbox):** запуск программы в изолированной виртуальной среде с жестким ограничением по времени (например, 30 секунд). Если за 30 секунд зловред не проявил активности, песочница вынуждена остановить анализ!

### 6.1 Проблема соответствий Поста (ПСП / Post Correspondence Problem)
В 1946 году Эмиль Пост сформулировал предельно простую по формулировке, но алгоритмически неразрешимую задачу из теории слов (комбинаторики).

Пусть дан набор из k доминошек (пар слов над конечным алфавитом). Каждая доминошка состоит из верхнего слова u<sub>i</sub> и нижнего слова v<sub>i</sub>:

```
  ┌────────┐  ┌────────┐  ┌────────┐
  │  u₁    │  │  u₂    │  │  u₃    │  ... (Верхний ряд)
  ├────────┤  ├────────┤  ├────────┤
  │  v₁    │  │  v₂    │  │  v₃    │  ... (Нижний ряд)
  └────────┘  └────────┘  └────────┘
     №1          №2          №3
```

> ❓ **Вопрос ПСП:** Можно ли выбрать последовательность номеров доминошек i<sub>1</sub>, i<sub>2</sub>, ..., i<sub>m</sub> (номера могут повторяться любое число раз), такую, чтобы составленное слово из верхних половинок в точности совпало со словом из нижних половинок:
> **u<sub>i1</sub> u<sub>i2</sub> ... u<sub>im</sub> = v<sub>i1</sub> v<sub>i2</sub> ... v<sub>im</sub>**?

#### Пример разрешимого частного случая:
Пусть даны 3 пары слов:
* Домино №1: верх `b`, низ `bbb`
* Домино №2: верх `babbb`, низ `ba`
* Домино №3: верх `a`, низ `a`

Попробуем составить совпадение. Возьмем последовательность доминошек: **(№2, №1, №1, №3)**:
* Верхний ряд: `u₂ u₁ u₁ u₃` = `(babbb) + (b) + (b) + (a)` = **babbbba**
* Нижний ряд: `v₂ v₁ v₁ v₃` = `(ba) + (bbb) + (bbb) + (a)` = **babbbbbba** — не совпало!

А если взять последовательность: **(№1, №2, №1, №3)**?
* Верх: `u₁ u₂ u₁ u₃` = `b + babbb + b + a` = **bbabbba**
* Нижний ряд будет другим.

Эмиль Пост строго доказал: **не существует алгоритма, который для произвольного произвольно заданного набора доминошек за конечное время определяет, существует ли последовательность решения.**

### 6.2 Десятая проблема Гильберта (Диофантовы уравнения)
В 1900 году на II Международном конгрессе математиков в Париже Давид Гильберт поставил задачу №10:
> *«Разработать общий универсальный метод (алгоритм), позволяющий для произвольного алгебраического диофантова уравнения с целыми коэффициентами определить в целых числах, имеет ли оно хотя бы одно решение».*

Диофантово уравнение — это уравнение вида:
`P(x₁, x₂, ..., xₙ) = 0`, где P — многочлен с целыми коэффициентами, а решения ищутся в целых числах (например, x<sup>3</sup> + y<sup>3</sup> = z<sup>3</sup>).

Математики безуспешно искали такой алгоритм 70 лет. В 1970 году 23-летний советский математик **Юрий Владимирович Матиясевич**, опираясь на работы американских исследователей Мартина Дэвиса, Хилари Патнэма и Джулии Робинсон (коллективная теорема DPRM), поставил финальную точку:
> 🏆 **Теорема Матиясевича (1970):**
> **Десятая проблема Гильберта алгоритмически неразрешима.** 
> Единого универсального алгоритма для выяснения разрешимости диофантовых уравнений в целых числах существовать не может.

### 6.3 Проблема замощения плоскости плитками Вана (Wang Tiles / Domino Problem)
В 1961 году философ и логик Ван Хао (Hao Wang) предложил задачу:
* Имеются квадратные плитки одинакового размера с цветными ребрами.
* Плитки нельзя вращать или переворачивать.
* Можно ли замостить ими всю бесконечную плоскость так, чтобы соседние плитки соприкасались ребрами одинакового цвета?

Ван Хао предполагал, что если плоскость можно замостить, то ее всегда можно замостить периодически (повторяющимся узором), а значит, алгоритм проверки существует. 
Однако в 1966 году его ученик **Роберт Бергер (Robert Berger)** доказал:
1. Существуют непериодические наборы плиток (замощение плоскости возможно, но узор никогда не повторяется периодически).
2. **Задача замощения плитками Вана алгоритмически неразрешима.**

### 6.4 Метод сведения (Turing Reduction)
Как ученые доказывают, что очередная новая задача `B` алгоритмически неразрешима? Ведь нельзя каждый раз строить парадокс с нуля!

Для этого используют мощнейший математический аппарат — **метод сведения (редукции)**:
1. Берется уже известная неразрешимая задача `A` (например, проблема останова Тьюринга).
2. Предполагается от противного, что для новой задачи `B` алгоритм решения найден.
3. Показывается, что если бы мы умели решать задачу `B`, то, переведя данные задачи `A` на язык задачи `B`, мы смогли бы решить и задачу `A`!
4. Но задача `A` заведомо неразрешима! Следовательно, наше предположение ложно, и задача `B` также гарантированно **алгоритмически неразрешима**.

Именно через сведение проблемы остановки машины Тьюринга были доказаны неразрешимость Проблемы соответствий Поста, теоремы Райса, задачи замощения плоскости и 10-й проблемы Гильберта!

## 7. Дополнительная информация. Задание 1 (Уровень 1: Базовый практикум) 🧩

### 7.1 Схема инвертора в доказательстве Тьюринга (Коммутация проводов)
Внимательно проанализируйте логическую цепь конструирования диагональной программы `D`:
1. **Входной аргумент:** исходный код анализируемой программы `P`. Он подается на приемник дубликатора аргументов.
2. **Блок дублирования входов:** формирует пару аргументов `(P, P)`.
3. **Блок гипотетического оракула H:** принимает пару `(P, P)` и выносит вердикт `H(P, P)`: сигнал `True` (останавливается) или `False` (зацикливается).
4. **Блок логического инвертора реакции:**
   * Получив вердикт `True` от `H`, блок активирует вечный цикл (`while True: pass`);
   * Получив вердикт `False` от `H`, блок переходит в терминальное состояние (мгновенный штатный останов `return` / `q₀`).

> 💡 **Правило коммутации:** Соединяйте исходящие порты оракула со входами соответствующих исполнительных узлов **строго по принципу инверсии**: сигнал завершения `True` обязан вести к вечному циклу, а сигнал зацикливания `False` — к мгновенной остановке. Любое прямое соединение (True ➔ останов) нарушает доказательство парадокса!

### 7.2 Классификация свойств по теореме Райса (Сортировка по контейнерам)
Вам потребуется распределять аналитические карточки по двум функциональным контейнерам:
* **Контейнер 1: «Синтаксические свойства (Разрешимые)»:**
  * Проверка соответствия и парности круглых скобок `(` и `)`;
  * Наличие импорта конкретного модуля (например, `import math`);
  * Подсчет общего количества строк кода и символов в файле;
  * Наличие необъявленных идентификаторов (статический контроль типов);
  * Поиск зарезервированного ключевого слова `while` в тексте программы;
  * Проверка длины строк и идентификаторов по стандарту PEP 8.
* **Контейнер 2: «Семантические свойства (Неразрешимые по Райсу)»:**
  * Проверка равенства возвращаемого значения константе `0`;
  * Проверка достижения аварийной инструкции деления на ноль;
  * Определение эквивалентности двух функций разной структуры;
  * Выяснение, завершит ли программа работу на всех натуральных числах;
  * Детектирование мертвого кода (вызов функции никогда не выполнится);
  * Проверка, выведет ли когда-нибудь программа на экран заданную строку.

### 7.3 Сборка цепочек соответствия в задаче Поста (Слот-пазл доминошек)
В третьей фазе необходимо составить последовательность из пар слов (доминошек), чтобы составленное верхнее слово в точности совпало с нижним: `u₁ u₂ ... uₖ = v₁ v₂ ... vₖ`.
* **Стратегия подбора первого элемента:** Первой в цепочке обязана стоять доминошка, у которой **первые символы верхнего и нижнего слова совпадают** (например, верх начинается на `a` и низ начинается на `a`). Если первые символы различаются, совпадение недостижимо в принципе.
* **Баланс длин:** Если верхнее слово доминошки длиннее нижнего (например, верх `ab`, низ `a`), то верх опережает низ на символ `b`. Следующая доминошка обязана начинаться снизу с символа `b`, чтобы компенсировать отставание нижнего ряда.

## 8. Дополнительная информация. Задание 2 (Уровень 2: Продвинутый практикум) 🔍

На продвинутом уровне исключены подсказки: вам потребуется вручную рассчитывать трассировки, доказывать свойства циклов, анализировать предикаты и рассчитывать метрики статического анализа. Ответы вводятся с клавиатуры в поля ввода.

### 8.1 Анализ завершаемости конкретных циклов: Инварианты и функции спуска
Для доказательства остановки конкретного алгоритма используется математический метод **функции спуска (варианта цикла)**:
* Находится целочисленная величина `V`, зависящая от переменных программы.
* Доказывается, что на каждом шаге цикла величина `V` строго уменьшается: `V<sub>k+1</sub> < V<sub>k</sub>`.
* Доказывается, что величина `V` ограничена снизу: `V ≥ 0`.
* Так как бесконечно убывать в множестве неотрицательных целых чисел невозможно, цикл обязан остановиться за конечное число итераций.

#### Пример трассировки целочисленного деления:
```python
a = 35
b = 8
steps = 0
while a >= b:
    a = a - b
    steps = steps + 1
```
Вариант цикла: величина `a`. Начальное значение: 35.
1. Шаг 1: `a = 35 - 8 = 27`, `steps = 1`
2. Шаг 2: `a = 27 - 8 = 19`, `steps = 2`
3. Шаг 3: `a = 19 - 8 = 11`, `steps = 3`
4. Шаг 4: `a = 11 - 8 = 3`, `steps = 4`
5. Шаг 5: проверка `3 >= 8` ложна ➔ выход из цикла.
Итоговое значение `steps = 4` (в точности равно результату целочисленного деления: `35 // 8 = 4`).

### 8.2 Детектирование бесконечных циклов через инварианты четности (Ввод -1)
Если в цикле вида `while x != target: x = x + step` переменная `x` стартует с нечетного значения (например, 3) и увеличивается с четным шагом (например, `step = 2`), то значение `x` на всех итерациях **гарантированно остается нечетным**:
* Если целевое значение `target` является **четным** (например, 14), равенство `x == target` не может быть выполнено никогда!
* Цикл никогда не завершится самостоятельно (**Infinite Loop**).
* **Правило ввода в тренажере:** Если цикл зацикливается навсегда, в поле ввода вводится число **`-1`**. Если цикл останавливается штатно, вводится точное число итераций.

### 8.3 Трассировка парадокса Тьюринга: Предикаты HALT и LOOP
Вспомним определение программы `D`:
```python
def D(P):
    if H(P, P) == True:
        while True: pass  # LOOP (бесконечный цикл)
    else:
        return            # HALT (штатный останов)
```
* **Случай 1:** Анализатор утверждает `H(D, D) == True` (предсказывает, что программа остановится). В этом случае выполняется ветка `if`, программа входит в `while True: pass`, и ее фактическое поведение — **`LOOP`**!
* **Случай 2:** Анализатор утверждает `H(D, D) == False` (предсказывает зацикливание). В этом случае выполняется ветка `else: return`, и ее фактическое поведение — **`HALT`**!
* **Формат ввода:** В поле ввода необходимо набрать текстовый идентификатор фактического исхода: **`LOOP`** или **`HALT`** (регистр не имеет значения).

### 8.4 Конкатенация цепочки в ПСП Поста и запись результирующего слова
В задании даны доминошки: например, №1 `[a / ab]`, №2 `[b / a]`, №3 `[ab / b]`.
Задана последовательность номеров: `(1, 2, 3)`.
Выполняем пошаговую конкатенацию:
* Верхний ряд `U`: `u₁ + u₂ + u₃ = 'a' + 'b' + 'ab' = 'abab'`
* Нижний ряд `V`: `v₁ + v₂ + v₃ = 'ab' + 'a' + 'b' = 'abab'`
Поскольку `U === V`, результирующим словом является строка **`abab`**. Ее необходимо ввести в поле ввода символ за символом.

### 8.5 Математические формулы метрик SAST-анализа (False Positives и False Negatives)
При статическом анализе кода кодовой базы:
* **RealBugs** — общее число функций, реально содержащих уязвимости.
* **Alerts** — общее число предупреждений, выданных анализатором.
* **TP (True Positives)** — истинные срабатывания (реальные баги, верно найденные анализатором).

Из этих базовых величин однозначно рассчитываются ошибки анализатора:
1. **False Positives (FP, ложные тревоги):** число случаев, когда анализатор выдал предупреждение на чистый, безопасный код:
   `FP = Alerts - TP`
   *Пример:* если выдано 60 предупреждений, из которых 40 оказались реальными багами, то ложных тревог: `60 - 40 = 20`.
2. **False Negatives (FN, пропущенные баги):** число реальных уязвимостей, которые анализатор пропустил и не обнаружил:
   `FN = RealBugs - TP`
   *Пример:* если в проекте было 45 реальных багов, а анализатор нашел только 40, то пропущено: `45 - 40 = 5` уязвимостей.

## 9. Дополнительная информация. Задание 3 (Уровень 3: Аркада / Босс) ⚡

Финальный уровень — скоростное аркадное испытание («Защитный шлюз Райса») под жестким таймером тревоги. Малейшая ошибка или тайм-аут вызывают аварию ядра (`KERNEL PANIC`) и полностью сбрасывают весь прогресс на Волну 1.

### 9.1 Архитектура шлюза безопасности (Rice Security Gateway)
На шлюз ядра поступают исполняемые модули. Вам необходимо за секунды проанализировать микрокод и применить одно из трех решений перехвата (кнопки на экране или клавиши `1`, `2`, `3` на клавиатуре):

1. **Решение `[1] ALLOW` (Пропустить легитимный код):**
   * Применяется, когда алгоритм имеет строго доказанный останов (например, рекурсивный алгоритм Евклида для поиска НОД, цикл с доказанным монотонным убыванием функции спуска `V = count` до нуля).
   * Попытка заблокировать такой код вызывает ошибку **False Positive** (ложная тревога, блокировка критической службы ОС) и приводит к сбросу!
2. **Решение `[2] SANDBOX` (Изолировать в поведенческую песочницу):**
   * Применяется, когда алгоритмическая остановка не доказана теоретически либо зависит от внешнего потока данных:
     * Сиракузская последовательность (гипотеза Коллатца `3n + 1`) — открытая математическая проблема, остановка не гарантирована;
     * Потоковые сетевые парсеры, размер чанков которых определяется внешней сетью.
3. **Решение `[3] BLOCK` (Немедленно заблокировать угрозу):**
   * Применяется при наличии очевидного деструктивного или вечного циклического поведения:
     * Гарантированный вечный цикл: `while True: pass`, либо цикл с несовпадением инварианта четности;
     * Вредоносная модификация ядра: прямое шифрование загрузочного сектора MBR без запроса пользователя;
     * Семантический парадокс Тьюринга: программа `D(D)` с инверсией оракула останова;
     * Полиморфный эксплойт с вечным побитовым переполнением регистра.
   * Пропуск такого кода вызывает ошибку **False Negative** (проникновение вредоноса в память) и приводит к аварии ядра!

### 9.2 Экспресс-паттерны скоростного анализа циклов под таймером
* **Зависание по четности:** Если `x` стартует с нечетного числа, увеличивается на `+2`, а условие выхода `x != 10` — цель недостижима, цикл вечен ➔ жмите **`[3] BLOCK`**!
* **Коллатц 3n + 1:** Если видите правило `if n % 2 == 0: n //= 2 else: 3*n + 1` — это классическая неразрешимая гипотеза ➔ жмите **`[2] SANDBOX`**!
* **Алгоритм Евклида:** Если видите `while b != 0: a, b = b, a % b` — это доказанный алгоритм НОД ➔ жмите **`[1] ALLOW`**!
* **Шифрование диска MBR:** Если видите обращение к `\\.\PhysicalDrive0` или прямое зануление диска ➔ жмите **`[3] BLOCK`**!

### 9.3 Регламент горячих клавиш для максимальной скорости
Для победы на 8 волнах рекомендуется использовать клавиатурный перехват:
* Клавиша **`1`** (или **`A`**) — `ALLOW`
* Клавиша **`2`** (или **`S`**) — `SANDBOX`
* Клавиша **`3`** (или **`D`**) — `BLOCK`
Это позволяет реагировать за доли секунды, удерживая запас времени до тайм-аута.
