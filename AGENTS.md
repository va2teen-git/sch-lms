# ИНСТРУКЦИИ ДЛЯ ИИ (DISPATCHER)

Вы работаете над образовательной платформой School LMS (на базе Astro).
**В целях экономии контекста базовая документация разделена на модули.**

> ⚠️ **КРИТИЧЕСКОЕ ПРАВИЛО: ИЗОЛЯЦИЯ ПРОДАКШНА И РАБОТА ЧЕРЕЗ GIT WORKTREE**
> Боевой сервер запущен на **ALT Linux** как `systemd`-сервис `school-lms.service` из каталога `~/Projects/school-lms` (порт **`3000`**, т.к. `8080` занят службой `ahttpd`) и обслуживает учащихся (`http://192.168.100.135:3000`).
> **КАТЕГОРИЧЕСКИ ЗАПРЕЩАЕТСЯ** в каталоге `~/Projects/school-lms`:
> 1. Переключать ветки Git (`git checkout`);
> 2. Запускать сборку (`npm run build`) в обход регламента деплоя;
> 3. Запускать dev-сервер (`npm run dev`) или автотесты (`npm test`, Playwright).
> Любое из этих действий приведет к повреждению сборки `dist/`, сбою боевого сервера или загрязнению боевой базы `telemetry.db`!
>
> **ПРАВИЛО РАЗРАБОТКИ:** Вся работа ИИ-агентов ведется **ИСКЛЮЧИТЕЛЬНО** в изолированном дереве `git worktree` на локальной ФС `ext4` (по умолчанию `~/Projects/school-lms-dev`, а при параллельной работе или когда первая ветка еще не очищена — в выделенных `~/Projects/school-lms-dev-2`, `~/Projects/school-lms-dev-3`).
> **ПОРТАТИВНЫЙ `agy` С ФЛЕШКИ (`vfat`):** при запуске `agy-portable` с USB-накопителя переменная `$HOME` подменяется на каталог флешки (`vfat`), а реальный домашний каталог лежит в `$REAL_HOME` (`/home/SCHOOL223.NET/vatutin_n_a`). Запрещено размещать проекты и `worktree` на `vfat`-флешке; для `npm` передавайте `HOME="$REAL_HOME"`, а для Playwright — `PLAYWRIGHT_BROWSERS_PATH="$REAL_HOME/.cache/ms-playwright"`.
> По завершении задачи и слиянии PR агент **ОБЯЗАН** удалить свой временный worktree (`rm ~/Projects/school-lms-dev-X/node_modules && git worktree remove ~/Projects/school-lms-dev-X --force` или через `manage_worktree`).
> Подробный регламент: см. `docs/ai-workflow.md`.

## 10. Регламент работы по пошаговому чек-листу (Checklist-Driven Workflow)
При поступлении задачи на разработку или продолжение урока (например, «Разрабатываем 7 класс, урок 9, Issue #352»):

1. **Анализ состояния и поиск чек-листа:**
   - Проверьте статус в Issue урока на GitHub (`gh issue view <ID>`) или локальный файл `src/content/lessons/<class_slug>/<lesson_id>/CHECKLIST.md`.
2. **Определение текущего шага:**
   - Найдите **первый невыполненный пункт** `- [ ]` в чек-листе. Выполняйте строго этот этап, не перескакивая вперед.
   - Загрузите в контекст только те модули документации из списка диспетчера выше, которые соответствуют этапу:
     * **Этап 1 (Базовая теория):** модули 6 (Учебный план) и 8 (AI Workflow). Раздел «Дополнительная информация» на данном этапе не создается.
     * **Этап 2 (Уровень 1):** модули 1 (Геймдизайн Ур. 1-2), 3 (Difficulty Curve), 4 (UI).
     * **Этап 3 (Уровень 2):** модули 1 (Геймдизайн Ур. 1-2), 3 (Difficulty Curve, кривая Sawtooth 2-1-2), 4 (UI).
     * **Этап 4 (Уровень 3):** модули 2 (Геймдизайн Ур. 3, банк архетипов), 3 (Difficulty Curve), 4 (UI).
     * **Этап 5 (Дополнительная информация):** модуль 6 (Zero-Leakage Policy под фактически созданные уровни).
     * **Этап 6 (Автотесты):** модуль 9 (Тестирование, Playwright E2E и цифровые персоны учащихся).
     * **Этап 7 (Релиз и деплой):** модуль 8 (AI Workflow: PR, слияние, очистка worktree, сборка dist и перезапуск боевого сервера).
3. **Фиксация прогресса:**
   - После выполнения этапа и проверки (линтером или тестами) замените `- [ ]` на `- [x]` в `CHECKLIST.md` и синхронизируйте тело Issue (`gh issue edit <ID> --body "..."`).
   - Сделайте атомарный коммит (`git commit`) и отправьте изменения в ветку (`git push`).
